# LangChain 도입 및 적용 가이드

> 이 문서는 현재 저장소의 구조를 기준으로 LangChain 도입 방식을 제안합니다. 지금부터 바로 의존성을 설치하거나 현재 화면을 AI 연동 상태라고 가정하지 않습니다. 먼저 프런트엔드와 백엔드의 책임 및 API 계약을 합의한 뒤 단계적으로 적용합니다.

## 1. 요약

이 프로젝트는 사용자가 아이디어를 입력하고, 아이디어를 PSST(Problem, Solution, Scale-up, Team) 기준으로 구체화한 다음 사업계획서와 진단 결과를 확인하는 서비스입니다. 따라서 LangChain은 화면 컴포넌트에서 직접 호출하는 UI 라이브러리가 아니라 **백엔드에서 LLM 호출과 문서 검색, 결과 검증을 구성하는 오케스트레이션 계층**으로 두는 것이 적절합니다.

권장 원칙은 다음과 같습니다.

1. 브라우저는 기존 API 클라이언트(`httpClient`)를 통해 백엔드에 요청합니다.
2. 모델 API 키, 시스템 프롬프트, 검색 권한, LangChain 호출은 서버에만 둡니다.
3. 고정된 PSST 분석 흐름은 우선 순차 파이프라인으로 구현합니다. 초기부터 자율 에이전트나 복잡한 다중 에이전트 구조를 도입하지 않습니다.
4. 모델 응답은 자유 형식 문자열이 아니라 버전이 있는 구조화 데이터로 받으며, 스키마 검증을 통과한 데이터만 저장하고 화면에 전달합니다.
5. 더미 수치와 실제 근거를 구분합니다. 근거가 없는 시장 규모·재무 목표·심사 점수를 모델이 사실처럼 만들어내지 않도록 합니다.
6. RAG는 실제 사용 권한이 있는 자료와 프로젝트별 문서가 준비된 뒤 추가합니다. 문서 검색은 출처와 접근 권한을 함께 다룹니다.

## 2. 현재 저장소에서 확인된 상태

| 영역 | 현재 상태 | 도입에 미치는 영향 |
|---|---|---|
| 프런트엔드 | Next.js 16, React 19, TypeScript 기반 | 브라우저 UI는 기존 API 계층을 통해 분석을 요청하는 구조가 자연스럽습니다. |
| API 클라이언트 | `api/index.ts`에서 Axios 인스턴스를 만들고 `NEXT_PUBLIC_API_BASE_URL`을 사용합니다. 기본 주소는 `http://127.0.0.1:8000`입니다. | 해당 주소가 가리키는 API 서버가 모델 호출을 수행할 후보입니다. 실제 백엔드 언어와 프레임워크는 이 저장소만으로 확인할 수 없습니다. |
| API 모듈 | `api/auth.ts`, `api/user.ts`, `api/email-verification.ts` 등 인증·프로필 API가 있습니다. | AI API도 기존 규칙에 맞춰 별도의 API 모듈로 추가할 수 있습니다. |
| 프롬프트 UI | `components/common/app-context.tsx`에 아이디어 입력용 `Textarea`와 제출 버튼이 있으나 상태 연결이나 분석 요청은 없습니다. | 실제 요청 상태, 검증, 오류, 재시도 UX를 붙여야 합니다. 현재 선택 아이디어 카드와 첨부 소스도 하드코딩되어 있습니다. |
| 워크스페이스 상태 | `store/workspace.ts`에는 현재 `idea`/`analytics` 화면 상태만 있습니다. | 선택 프로젝트와 분석 결과가 필요해지면 기존 화면 전환 상태와 결과/프로젝트 도메인 상태를 구분해야 합니다. |
| 보고서 | `components/report/`의 사업계획서 섹션은 정적 더미 콘텐츠입니다. | 분석 API 결과를 화면에 바인딩하기 전, 섹션별 데이터 계약을 정의해야 합니다. |
| LangChain | 현재 `package.json`에 LangChain 패키지가 없고 검색된 코드에도 실제 LLM 실행 코드가 없습니다. | 아직 프런트엔드나 백엔드 어디에도 LangChain이 도입된 것으로 간주하면 안 됩니다. |

> `README.md`는 프런트엔드 추가 요구사항과 백엔드 예정 작업을 기술하고 있지만, 현재 저장소에는 해당 백엔드 구현이 포함되어 있지 않습니다. 따라서 LangChain을 둘 위치와 서버 언어는 실제 API 서버 저장소를 확인한 뒤 결정해야 합니다.

## 3. 권장 아키텍처

```text
┌─────────────────────────────────────────────┐
│ Next.js 프런트엔드                           │
│ AppContext → 분석 요청 → 진행/오류 상태       │
│ 사업계획서 탭 ← 검증된 분석 결과 렌더링        │
└──────────────────────┬──────────────────────┘
                       │ HTTPS + 로그인 세션
                       │ POST /api/v1/projects/{projectId}/analyses
                       ▼
┌─────────────────────────────────────────────┐
│ 기존 API 서버 (현재 프런트엔드 기본 URL :8000) │
│ 인증·인가 → 요청 검증 → 분석 작업 관리         │
│                                             │
│ AI 애플리케이션 서비스                        │
│ 입력 정규화 → 자료 검색(선택) → PSST 생성      │
│ → 출력 검증 → 점수/근거 계산 → 저장            │
│                                             │
│ LangChain 어댑터 → 모델 제공자 API             │
└──────────────────────┬──────────────────────┘
                       │ 선택적 RAG
                       ▼
┌─────────────────────────────────────────────┐
│ 프로젝트별 문서 저장소 / 메타데이터 DB / 벡터 검색 │
└─────────────────────────────────────────────┘
```

### 배치 위치 선택

**권장: LangChain은 이미 API 요청을 받는 별도 백엔드에 둡니다.**

- `NEXT_PUBLIC_API_BASE_URL`과 인증 API가 존재하므로, 프런트엔드가 사용하는 API 서버가 백엔드 책임을 갖는 것으로 보입니다.
- 모델 키가 `NEXT_PUBLIC_*` 변수로 노출되는 사고를 방지할 수 있습니다.
- 사용자 인증, 프로젝트 권한, 파일 접근 권한, 요청 제한, 결과 저장을 한 서버에서 일관되게 처리할 수 있습니다.
- 백엔드가 Python이면 LangChain Python, Node.js/TypeScript이면 LangChain JS/TS를 검토합니다. **프런트엔드가 TypeScript라고 해서 백엔드까지 LangChain JS를 써야 하는 것은 아닙니다.**

**대안: 백엔드가 아직 없을 때만 Next.js Route Handler를 얇은 서버 프록시로 검토합니다.**

- 기존 API 서버를 대체할지, Next.js가 AI 전용 백엔드가 될지 먼저 정해야 합니다. 두 서버에 비즈니스 로직을 중복 구현하지 않습니다.
- 서버 컴포넌트나 클라이언트 컴포넌트에서 공급자 SDK를 직접 호출하지 않습니다.
- Route Handler를 선택한다면 인증 확인, 사용자별 권한, 요청 제한, 타임아웃, 결과 저장을 함께 설계합니다.
- 현재 Next.js 버전은 `16.3.4`이므로 Route Handler의 런타임·캐시·스트리밍 동작은 구현 시 설치된 버전의 공식 문서를 확인합니다.

## 4. 도입 전에 먼저 결정할 것

### 4.1 API 서버의 소유권과 언어

다음 사항은 코드만으로 확인되지 않습니다.

- 포트 `8000`의 백엔드 저장소와 실제 배포 주소
- 백엔드 언어/프레임워크
- 사용자 인증 토큰을 백엔드에서 검증하는 방식
- 프로젝트·분석 결과·업로드 문서의 현재 DB 스키마
- 사용할 모델 제공자, 리전, 데이터 보존 정책

LangChain 패키지를 설치하기 전에 백엔드 저장소 담당자와 이 항목을 확인합니다. LangChain JS와 Python을 양쪽에 동시에 도입하면 프롬프트와 검증 로직이 중복될 수 있으므로, 오케스트레이션 소유자를 한 곳으로 정합니다.

### 4.2 분석 결과의 의미

AI 결과에서 아래 값을 어떤 기준으로 제공하는지 합의해야 합니다.

- PSST 초안: 사용자 입력과 제공 자료를 바탕으로 한 생성 결과
- 정량 점수: 명시적인 평가 루브릭에 따라 계산한 진단 점수
- 시장/재무 수치: 출처로 검증한 값, 사용자 입력 값 또는 명시된 가정 값
- 적합도: 특정 지원사업의 공개된 평가 지표에 대한 참고 분석

모델이 생성한 점수나 근거 없는 통계를 실제 심사 점수, 공식 통계, 합격 확률처럼 표현하면 안 됩니다. 기준이 부족하면 숫자 대신 “자료 부족”, “가정 필요”, “추가 검증 권장”을 반환하게 합니다.

### 4.3 동기 응답인지 비동기 작업인지

초기 PoC는 요청 한 번에 결과를 반환하는 동기 API로 시작할 수 있습니다. 입력 문서가 많거나 분석이 오래 걸리는 경우에는 작업 ID를 반환하는 비동기 API와 상태 조회/이벤트 스트림을 추가합니다. 먼저 실제 처리 시간과 모델 제공자의 타임아웃을 측정하고 전환 시점을 정합니다.

## 5. 프런트엔드 통합 설계

### 5.1 UI 컴포넌트의 책임

`AppContext`는 아이디어와 선택된 문서 ID 등 사용자 입력을 수집하고, 제출·로딩·오류 상태를 화면에 표시하는 역할로 제한합니다.

권장 흐름:

1. 사용자가 아이디어를 입력하고 분석 버튼을 누릅니다.
2. 필수 입력과 요청 중복 여부를 검사합니다.
3. 선택된 프로젝트 ID, 입력 내용, 참조 문서 ID를 AI API 모듈로 전달합니다.
4. 진행 상태를 표시하고 취소/재시도 정책을 적용합니다.
5. 성공 응답을 분석 결과 상태에 저장하고 기존 PSST/report UI에 전달합니다.
6. 실패 응답을 사용자에게 설명 가능한 형태로 표시합니다. 더미 분석 결과로 성공처럼 대체하지 않습니다.

### 5.2 프런트엔드 모듈 배치 예시

실제 프로젝트 컨벤션에 맞춰 조정하되, 도메인별 API·타입·훅·UI의 책임을 분리합니다.

```text
api/
  idea-analysis.ts          # httpClient 기반 요청 함수
types/
  idea-analysis.ts          # 요청/응답 타입
hooks/
  use-idea-analysis.ts      # mutation, 로딩/오류 상태
components/
  common/app-context.tsx    # 입력과 제출 UX
  report/                   # 검증된 결과 표시
```

현재 프로젝트에는 이미 도메인 API 모듈(`api/auth.ts`, `api/user.ts`) 패턴이 있으므로 이를 따릅니다. TanStack Query 등 새 서버 상태 라이브러리는 중복 요청·캐시·폴링 요구사항을 확인하기 전에는 추가하지 않습니다.

### 5.3 환경 변수와 비밀 정보

- `NEXT_PUBLIC_API_BASE_URL`: 브라우저가 호출하는 백엔드의 공개 URL만 둡니다.
- `OPENAI_API_KEY`, `ANTHROPIC_API_KEY` 등 모델 키는 백엔드의 비공개 환경 변수/Secret Manager에만 둡니다.
- 모델 키를 `NEXT_PUBLIC_`로 시작하는 환경 변수에 절대로 넣지 않습니다.
- 브라우저 번들, 오류 응답, 로그, 소스맵에 비밀 정보가 들어가지 않도록 검사합니다.

## 6. 백엔드의 도메인 경계

LangChain 코드를 API 라우트 함수 하나에 모두 넣기보다, 아래 책임으로 나눕니다. 디렉터리명은 백엔드 언어에 맞춰 변경합니다.

```text
idea_analysis/
  api/                  # HTTP 입력/출력, 인증된 사용자 컨텍스트
  schemas/              # 요청/응답 및 모델 출력 스키마
  application/          # 분석 유스케이스와 파이프라인
  prompts/              # 버전 관리되는 시스템/작업 프롬프트
  retrieval/             # 파일 추출, chunk, 검색, 인용 근거 (RAG 단계)
  providers/             # 모델/임베딩 구현체 연결
  repositories/          # 프로젝트, 분석, 근거 저장소 인터페이스
  evaluation/            # 골든셋 및 품질 측정
```

핵심 원칙:

- HTTP 핸들러는 인증·요청 파싱·상태 코드 처리에 집중합니다.
- 애플리케이션 서비스는 입력, 프로젝트 정보, 문서 근거를 받아 PSST 분석 유스케이스를 실행합니다.
- 프롬프트는 코드 상수나 별도 프롬프트 파일로 버전 관리하고, 사용자 값은 명시적인 변수로 전달합니다.
- 공급자별 모델 설정은 어댑터에서 관리해 모델 교체가 도메인 로직을 흔들지 않도록 합니다.
- LangChain을 사용하더라도 도메인 타입과 저장 인터페이스가 LangChain 객체에 종속되지 않게 합니다.

## 7. API 계약 제안

아래는 기존 REST 경로 규칙(`/api/v1/...`)에 맞춘 **초안**입니다. 실제 라우트와 저장 모델을 확인한 뒤 확정해야 합니다.

### 7.1 분석 요청

```http
POST /api/v1/projects/{projectId}/analyses
Authorization: Bearer <access token or existing session>
Content-Type: application/json
```

```json
{
  "ideaText": "냉장고 속 남은 식재료를 활용해 1인 가구의 식재료 폐기를 줄이는 서비스",
  "referenceDocumentIds": ["doc_123", "doc_456"],
  "requestedSections": ["problem", "solution", "growth", "team"],
  "language": "ko"
}
```

`referenceDocumentIds`에는 브라우저가 임의 URL이나 파일 내용을 지정하는 대신 서버가 소유권을 확인할 수 있는 내부 문서 ID를 전달합니다.

### 7.2 성공 응답

  "sections": {

      "title": "문제인식",

        }
      ],

### 7.3 오류 응답

성공 형태의 기본값으로 오류를 숨기지 말고, 백엔드에서 안정적인 오류 코드를 정의합니다.

```json
{

    "code": "REFERENCE_DOCUMENT_FORBIDDEN",

  }

```

예상 코드: `INVALID_REQUEST`, `PROJECT_NOT_FOUND`, `REFERENCE_DOCUMENT_FORBIDDEN`, `RATE_LIMITED`, `MODEL_TIMEOUT`, `MODEL_UNAVAILABLE`, `OUTPUT_VALIDATION_FAILED`, `INTERNAL_ERROR`.

## 8. 분석 파이프라인 설계

### 8.1 1차 버전: 결정적인 단일 분석 파이프라인

```text
요청 검증
  → 사용자/프로젝트 권한 확인
  → 입력 길이·언어·첨부 문서 검사
  → 분석 실행(프롬프트 + 스키마 + 모델)
  → 구조화 출력 검증 및 정규화
  → 근거 없는 숫자/주장 탐지
  → 분석 버전과 사용 메타데이터 저장
  → 프런트엔드에 응답
```

PSST 각 영역은 한 번의 거대한 자유 형식 프롬프트보다, 같은 입력 컨텍스트와 공통 정책을 공유하되 목적이 분명한 단계로 나눌 수 있습니다. 다만 여러 차례 모델 호출은 지연 시간과 비용을 늘리므로 평가 결과가 이를 정당화할 때만 분리합니다.

권장 시작 형태:

1. 입력을 정규화하고, 미확인 사실을 `unknowns`로 수집합니다.
2. PSST 전체 결과를 하나의 제한된 구조화 출력으로 생성합니다.
3. 구조와 필수 필드를 서버에서 검증합니다.
4. 검증 실패 시 제한된 횟수만큼 오류 복구를 시도하거나 명시적 오류를 반환합니다.
5. 사용자에게 초안, 가정, 자료 부족 항목을 구별해 보여줍니다.

### 8.2 구조화 출력

LangChain의 구조화 출력과 백엔드 언어의 검증 스키마(Zod, Pydantic 등)를 함께 사용합니다. 모델이 타입을 선언했다는 이유만으로 출력이 안전하고 사실이라는 뜻은 아닙니다.

검증은 최소한 다음을 포함합니다.

- 필수 키·배열 길이·문자열 길이
- 점수 범위 및 최대 점수
- 통화 단위, 기간, 숫자 범위
- `evidenceIds`가 실제 검색 결과/저장된 근거를 참조하는지
- 없는 문서 ID, 존재하지 않는 인용 구절
- 보고서가 소비할 수 있는 `schemaVersion`

모델에게 숫자를 생성하게 둘 경우 `source` 또는 `basis`를 함께 받게 하고, 수치와 근거가 없으면 값을 비워두도록 설계합니다. TAM/SAM/SOM처럼 산식이 중요하면 가능한 한 근거 데이터와 명시적 산식으로 서버에서 계산합니다.

### 8.3 에이전트와 LangGraph는 나중에

초기 작업은 단계가 정해져 있고 기대 결과가 뚜렷합니다. 따라서 **LangChain의 모델·프롬프트·출력 파서/스키마·retriever 구성으로 시작하고 에이전트는 쓰지 않는 편**이 단순하고 테스트하기 쉽습니다.

아래 요구가 실제로 생기면 LangGraph를 검토합니다.

- 자료가 부족하면 질문하고 답변을 기다리는 반복 흐름
- 사람이 결과를 검토/승인한 후 다음 단계를 진행하는 흐름
- 중간 단계 저장·재개, 장시간 실행, 실패 복구가 필요함
- 분기, 반복, 도구 사용이 평가셋에서 실제 품질 개선을 보임

에이전트가 임의로 외부 도구를 실행하거나 결제·공고 제출·파일 공유 같은 중대한 작업을 수행하도록 하지 않습니다. 외부 작업은 권한 검사와 사용자의 확인을 받는 별도 서버 유스케이스로 제한합니다.

## 9. RAG 및 문서 자료 도입

현재 AppContext에 보이는 PDF/XLSX/PPTX 이름은 하드코딩 예시이며, 실제 업로드·텍스트 추출·벡터 인덱싱 구현으로 확인되지는 않습니다. 검색 기능을 약속하기 전에 전체 문서 수명주기를 구축해야 합니다.

### 9.1 문서 처리 흐름

```text
업로드 요청
  → 파일 형식/크기 검사 및 악성 파일 검사
  → 사용자·프로젝트 소유권과 저장 경로 연결
  → 서버 측 텍스트/표 추출
  → 원본 페이지/시트/슬라이드 메타데이터 보존
  → 의미 단위 chunk 분할
  → 임베딩 생성 및 인덱싱
  → 분석 시 projectId + 권한 범위로 검색
  → 근거 인용과 위치를 결과에 저장
```

### 9.2 RAG 안전·품질 요건

- 업로드 문서의 텍스트는 신뢰할 수 없는 데이터입니다. 문서 내부의 “시스템 지시를 무시하라” 같은 문자열을 실행 지침으로 취급하지 않습니다.
- 검색은 반드시 인증된 사용자의 프로젝트 범위에 한정하고, 검색 단계에서도 권한 필터를 적용합니다. 검색 후 UI에서 숨기는 것만으로는 권한 통제가 되지 않습니다.
- 벡터 저장소에 `userId`, `projectId`, `documentId`, `page/sheet/slide` 등의 메타데이터를 저장하고 삭제·권한 변경 시 인덱스도 동기화합니다.
- 원문 근거와 모델 생성 문장을 구분하고, 인용한 페이지/시트 등 위치를 반환합니다.
- 검색된 문서가 답을 뒷받침하지 않으면 문서 내용으로 단정하지 말고 근거 부족을 응답합니다.
- 민감정보 마스킹, 보존 기간, 사용자 삭제 요청 시 원문·청크·임베딩의 삭제 정책을 정의합니다.
- 청킹 크기나 임베딩 모델을 임의로 고정하지 말고 대표 자료 평가셋에서 검색 품질과 비용을 비교합니다.

### 9.3 RAG를 먼저 도입할지 여부

초기에는 사용자 입력만으로 PSST 초안을 생성하는 작은 PoC를 만들고, 보고서 초안 품질을 측정한 뒤 RAG를 추가하는 순서를 권장합니다. 실제 사용자 제공 자료가 핵심 품질을 좌우한다면 문서 업로드 및 출처 추적을 첫 번째 범위에 포함하되, 벡터DB 선택 전에 PDF/XLSX/PPTX 추출 품질을 먼저 검증합니다.

## 10. 데이터 저장 및 분석 이력

분석 결과를 화면 상태에만 두면 새로고침·다른 기기 사용·재분석 비교가 어려워집니다. 사용자/프로젝트 모델을 확인한 뒤 다음 정보를 서버 측에 저장하는 방안을 검토합니다.

- `analysisId`, `projectId`, `userId`
- 정규화된 입력 또는 개인정보를 제거한 입력 참조
- 결과 JSON과 `schemaVersion`
- prompt 버전, 모델 제공자/모델 식별자, 생성 파라미터
- 사용한 문서 ID 및 evidence locator
- 요청 시각, 완료 상태, 지연 시간, 재시도 횟수
- 토큰/사용량/비용(제공자가 허용하고 정책상 저장 가능한 범위)
- 사용자 수정본과 원본 AI 초안의 분리

API 비밀키, 인증 토큰, 전체 업로드 원문, 불필요한 개인정보를 분석 로그에 남기지 않습니다. 프롬프트 전체를 로그로 보관해야 한다면 접근 권한, 마스킹, 보존 기한을 먼저 정합니다.

## 11. 평가와 테스트 전략

LangChain 도입은 “응답이 온다”만으로 완료되지 않습니다. 변경 가능한 프롬프트와 모델을 품질 기준으로 검증해야 합니다.

### 11.1 골든셋

실제 사용자 자료를 무단으로 복사하지 않고, 개인정보를 제거하거나 합성한 대표 입력을 만듭니다. 각 입력에 대해 기대하는 최소 결과를 정합니다.

- PSST 핵심 항목 누락 여부
- 사용자 입력과 무관한 주장 생성 여부
- 근거 인용 정확성
- 수치/기간의 단위 일관성
- 자료가 없을 때 불확실성을 표시하는지
- 특정 사용자·프로젝트 문서가 다른 프로젝트 결과에 섞이지 않는지
- 한글 문장 품질과 사업계획서 표현의 적합성

### 11.2 자동 테스트 레이어

1. **단위 테스트**: 입력 정규화, 검증, 권한 필터, 수치 산식, 출력 변환.
2. **스키마 테스트**: 유효/무효 모델 출력, 경계 점수, 빈 배열, `null`.
3. **파이프라인 통합 테스트**: 모델 제공자는 mock/fake로 대체해 분기와 오류 처리를 검사.
4. **검색 테스트**: 검색 결과 재현율, 올바른 페이지 인용, 교차 프로젝트 누출 방지.
5. **오프라인 품질 평가**: 프롬프트/모델 변경 전후 골든셋 비교.
6. **프런트엔드 테스트**: 제출 중복 방지, 로딩, 성공, 실패, 재시도, 취소 상태.
7. **제한된 운영 검증**: 비용 한도와 요청 제한이 설정된 스테이징 키로 소수 케이스 실행.

LLM의 표현은 비결정적일 수 있으므로 응답 전체 문자열을 스냅샷으로 고정하기보다 필드, 사실성, 근거 연결, 출력 형식 등 의미 있는 기준을 검사합니다.

## 12. 보안·신뢰성·비용

### 보안

- 백엔드에서 매 요청마다 사용자 인증과 프로젝트/문서 소유권을 확인합니다. 프런트엔드가 전달한 `userId`를 신뢰하지 않습니다.
- 입력 길이, 첨부 개수/크기, 동시 실행 수를 제한합니다.
- 사용자 입력과 검색 문서의 프롬프트 인젝션을 방어하고, 시스템 지침과 데이터 컨텍스트를 분리합니다.
- 모델 출력은 화면에 렌더링하기 전에 스키마 검증하고, HTML로 해석하지 않습니다.
- 모델이 반환한 URL을 자동 호출하지 않습니다. 외부 링크/도구 호출이 필요하면 허용 목록과 별도 검증을 둡니다.
- 사용자별 rate limit, 프로젝트별 quota, 악용 감지, 비용 상한을 마련합니다.
- 모델 제공자의 데이터 사용/보존 정책, 전송 리전, 계약상 데이터 처리 조건을 검토합니다.

### 신뢰성

- 공급자 호출의 타임아웃과 취소 전파를 정의합니다.
- 재시도는 일시적 네트워크 오류 등 재시도 가능한 오류에만 제한 횟수로 적용합니다. 검증 실패나 권한 실패를 무한 재시도하지 않습니다.
- 동기 요청 재시도에 따른 중복 비용/분석 저장을 방지할 수 있도록 idempotency key 또는 요청 중복 정책을 검토합니다.
- 공급자 오류를 성공 데이터로 바꾸지 않고 명시적 API 오류로 반환하며 `requestId`로 추적합니다.
- 모델/프롬프트 전환 시 이전 버전과 비교하고 점진적으로 배포합니다.

### 비용

- 모델별 입력/출력 토큰 및 분석당 비용을 계측합니다.
- 불필요한 문서 전문과 긴 대화 이력을 매번 전달하지 않습니다.
- 생성 결과를 캐시할 경우 프로젝트 권한, 입력 해시, 문서 인덱스 버전, 프롬프트 버전을 캐시 키에 반영합니다.
- 비용이 큰 모델/재시도/다단계 호출을 골든셋과 샘플 사용량으로 정당화합니다.
- 사용자가 재분석을 요청했을 때 새 분석인지, 기존 결과 재사용인지 UX와 과금 기준을 분명히 합니다.

## 13. 단계별 실행 계획

### 단계 0 — 백엔드와 데이터 흐름 확인

- 포트 `8000`의 API 서버 저장소/배포 환경/언어를 확인합니다.
- 인증 방식, 프로젝트 모델, 파일 저장 방식, DB를 확인합니다.
- 모델 제공자, 데이터 보존·전송 정책, 예산을 결정합니다.
- 분석 결과의 점수·근거·시장 수치 의미를 합의합니다.

**완료 기준:** LangChain을 실행할 서버와 책임자가 하나로 정해지고, 분석 요청/응답 초안이 프런트·백엔드 간 합의됩니다.

### 단계 1 — API 계약과 더미 연동

- 분석 입력·응답·오류 DTO와 출력 스키마를 정의합니다.
- AppContext 입력/제출/로딩/오류 UX를 구현합니다.
- API 모듈을 추가하되, 초기에는 명시적인 개발용 mock 서버 또는 테스트 fixture로 검증합니다.
- 기존 사업계획서의 정적 화면을 API 결과를 받을 수 있는 렌더링 경계로 정리합니다.

**완료 기준:** 모델 없이도 브라우저부터 report까지 같은 계약으로 성공/오류 상태를 검증할 수 있습니다. 개발용 fixture는 실제 결과로 오인되지 않게 표시합니다.

### 단계 2 — LangChain 단일 호출 PoC

- 백엔드에 LangChain과 선택한 공급자 통합 패키지를 설치합니다.
- 비공개 서버 환경 변수에 모델 키를 설정합니다.
- 고정된 작은 PSST 입력 집합으로 구조화 출력과 실패 경로를 구현합니다.
- 검색 없이 입력 텍스트만 사용해 품질·지연 시간·비용을 기록합니다.
- 사용자에게는 AI 생성 초안임을 표시하고 수정할 수 있도록 합니다.

**완료 기준:** 스키마 통과율, 실패 응답, 골든셋 품질, 분석당 비용/시간의 최소 수용 기준을 만족합니다.

### 단계 3 — 실제 분석 저장 및 보고서 연결

- 인증된 프로젝트에 분석 결과를 저장하고 재조회 API를 추가합니다.
- 프런트엔드가 선택 프로젝트별 분석 결과를 조회하도록 연결합니다.
- 다시 분석/이전 버전 비교와 사용자 편집 값의 저장 정책을 정합니다.
- 에러/로딩/빈 상태에서도 사업계획서 탭의 기존 레이아웃과 동작을 보존합니다.

**완료 기준:** 로그인한 사용자가 생성·새로고침·재조회할 수 있고, 다른 프로젝트 결과를 볼 수 없습니다.

### 단계 4 — 자료 업로드와 RAG

- 문서 업로드, 악성 파일 검사, 추출, 저장, 삭제 흐름을 먼저 구축합니다.
- 페이지/시트 위치를 보존하고 프로젝트별 권한 검색을 구현합니다.
- 인용 가능한 근거를 응답 스키마와 보고서 화면에 표시합니다.
- 자료 부족 시 답을 지어내지 않는 평가 케이스를 추가합니다.

**완료 기준:** 대표 PDF/XLSX/PPTX 자료에서 근거 위치가 올바르고, 사용자·프로젝트 간 자료 누출 테스트를 통과합니다.

### 단계 5 — 운영 고도화

- 비용·지연시간·오류·스키마 실패·사용자 수정률 계측
- 제한적 요청량에서 모델/프롬프트 A/B 및 회귀 평가
- 필요할 때 LangGraph 기반 장기 실행/승인 흐름 검토
- 관리자 재처리·분석 버전·보존/삭제 정책 운영

## 14. 구현 체크리스트

### 시작 전

- [ ] 별도 백엔드 저장소와 포트 `8000`의 소유자를 확인했다.
- [ ] LangChain을 둘 런타임과 담당 서비스를 정했다.
- [ ] 모델 제공자와 키 관리/데이터 처리 정책을 정했다.
- [ ] 분석 응답 스키마와 오류 코드를 프런트·백엔드가 합의했다.
- [ ] 점수와 TAM/SAM/SOM 등 수치의 근거 정책을 정했다.

### API/백엔드

- [ ] 사용자 인증 및 프로젝트 소유권을 백엔드에서 검증한다.
- [ ] 모델 키는 서버 비밀 저장소에서만 읽는다.
- [ ] 모델 출력 스키마를 검증하고 실패를 명시적으로 반환한다.
- [ ] 프롬프트·모델·스키마 버전을 기록한다.
- [ ] timeout, 제한 재시도, rate limit, 중복 요청 정책을 설정한다.
- [ ] 로그에 키, 인증정보, 불필요한 개인정보/원문이 남지 않는다.
- [ ] 결과와 문서 근거에 프로젝트 접근 권한을 적용한다.

### 프런트엔드

- [ ] `AppContext`가 실제 아이디어 입력값을 API에 전달한다.
- [ ] 제출 중 버튼 잠금, 진행/오류/재시도 상태를 처리한다.
- [ ] API 함수와 DTO 타입을 도메인 단위로 분리한다.
- [ ] 사업계획서 화면은 서버 응답을 렌더링하며 오류를 더미 성공으로 대체하지 않는다.
- [ ] 생성된 초안과 사용자 수정 내용을 구분한다.

### 품질/운영

- [ ] 골든셋과 프롬프트/모델 변경 회귀 테스트가 있다.
- [ ] 분석당 지연 시간과 비용을 측정한다.
- [ ] 실제 근거 없는 사실/수치를 탐지하는 검증 정책이 있다.
- [ ] 문서 접근 권한 및 삭제/인덱스 동기화 테스트가 있다.

## 15. 현재 프로젝트 기준 첫 PR 권장 범위

처음부터 LangChain·벡터DB·파일 파서·에이전트를 동시에 넣기보다 아래와 같이 작은 단위로 진행합니다.

1. 백엔드 저장소를 확인하고 소유권/인증/프로젝트 모델을 문서화합니다.
2. 프런트와 백엔드가 합의한 `POST /api/v1/projects/{projectId}/analyses` 계약을 정의합니다.
3. 프런트엔드에 `api/idea-analysis.ts`와 타입, AppContext의 입력/로딩/오류 상태를 추가합니다.
4. 백엔드에 단일 분석 유스케이스와 구조화 출력 검증을 붙입니다.
5. 하드코딩된 PSST 보고서 데이터를 한 번에 모두 교체하지 말고, 한 섹션부터 실제 응답 바인딩과 테스트를 수행합니다.
6. PoC 평가를 통과한 뒤에만 결과 저장, 문서 업로드/RAG, 스트리밍 순으로 확대합니다.

이 순서는 기존 사업계획서 UI를 먼저 보존하면서 AI 데이터 연결을 검증하고, 비용과 보안 위험을 통제할 수 있도록 합니다.
