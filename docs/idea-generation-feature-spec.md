# AppContext 아이디어 도출 기능 명세서

## 1. 문서 목적

이 문서는 `AppContext`의 아이디어 입력 `Textarea`와 하단 Send 버튼을 연결하여 사용자가 아이디어를 제출하고 분석 결과를 받는 기능의 요구사항을 정의합니다.

현재 구현은 FastAPI 백엔드의 파일 업로드, 아이디어 도출, 아이디어 선택 API를 호출합니다. 실제 응답 생성은 백엔드의 구현 및 실행 상태에 따르며, 프런트엔드 mock 결과로 대체하지 않습니다.

이 명세는 [LangChain 도입 및 적용 가이드](./langchain-adoption-guide.md)의 원칙을 따릅니다.

- 브라우저는 기존 API 클라이언트를 통해 서버에 요청합니다.
- 모델 호출, 프롬프트, 공급자 키는 서버에서 관리합니다.
- 모델의 자유 형식 답변을 바로 화면에 사용하지 않고 검증된 응답 계약을 사용합니다.
- 오류를 더미 성공 결과로 바꾸지 않습니다.
- 기존 UI 레이아웃과 사업계획서 화면을 보존합니다.

FastAPI 백엔드의 제안 API 계약, 파일 처리/권한, 응답 스키마, 오류 처리 및 백엔드 검수 기준은 [AppContext FastAPI 백엔드 기능 명세](./app-context-fastapi-backend-spec.md)를 참고합니다.

### 검토 결과 및 현재 구현 범위

FastAPI 라우터 계약에 따라 파일과 아이디어 API를 호출합니다. API 응답은 화면에 반영하기 전에 필수 필드와 아이디어 개수를 검사합니다.

- 참조 소스 컨텍스트 → 구조화 포커스 레이어 → 핵심 분석 아이디어 순으로 각 영역에 skeleton UI를 표시한 뒤 내용을 보여줍니다.
- 단계별 skeleton은 요청이 계속되는 동안 약 3초 간격으로 전환합니다. API 요청은 제출 즉시 시작하고, 응답이 도착하면 남은 대기 단계를 건너뛰어 결과 카드를 바로 표시합니다.
- 업로드는 `POST /api/v1/source-files`로 전송하고, 성공한 파일 ID들을 아이디어 도출 요청에 포함합니다.
- 실제 업로드 파일이 없으면 파일명을 임의로 표시하지 않고, 3개 파일 카드와 비슷한 높이의 참조 파일 없음 상태를 표시합니다.
- skeleton 카드의 줄 높이와 패딩은 실제 카드보다 과하게 커지지 않도록 맞춥니다.
- 핵심 분석 아이디어 3개는 App-Context와 메인 영역 모두에서 선택할 수 있고, 공용 확인 모달에서 구체화를 확정합니다.
- 확인 모달의 구체화 버튼을 누르면 `POST /api/v1/idea-generations/{generation_id}/selection` 이후 구체화 API를 호출합니다.
- 선택 강조는 inset ring 색상만 바꾸어 카드 레이아웃이나 크기를 이동시키지 않습니다.
- 제출 오류 및 입력 오류는 하단 인라인 메시지가 아니라 기존 전역 toast UI로 보여주며, 성공 메시지도 짧게 유지하고 아이콘을 텍스트 시작점에 정렬합니다.
- API 오류 또는 응답 검증 실패 시 실패 toast를 표시하고 입력값을 보존합니다.

## 2. 현재 상태와 구현 전제

### 확인된 현재 상태

- `components/common/app-context.tsx`의 `Textarea`는 controlled 입력이며 Send/Enter 제출, Shift+Enter 줄바꿈을 지원합니다.
- Send 시 참조 소스 → 구조화 포커스 → 아이디어 카드 순으로 skeleton을 표시합니다.
- `api/idea-generation.ts`가 파일 업로드, 아이디어 생성, 선택 저장 API를 호출합니다.
- 제안 카드 중 하나를 선택할 수 있고, 선택된 카드는 선택 표시와 테두리로 구분됩니다.
- 입력 및 생성 오류는 공통 toast UI로 표시합니다.
- 참조 소스 카드와 포커스 레이어는 백엔드 응답에 연결되어 있습니다.
- 최초 화면에서는 세 컨텍스트 영역 대신 프롬프트 입력을 권하는 안내 카드를 보여줍니다. 입력 중에는 화면을 바꾸지 않으며, Send 제출 후 응답을 기다리는 동안 세 컨텍스트와 순차 로딩 UI를 표시합니다. 결과가 반환되면 제안 카드를 계속 보여줍니다.
- 응답 대기 중 참조 소스, 구조화 포커스, 아이디어 결과 단계로 약 3초 간격으로 전환합니다. API 응답이 도착하면 대기 단계를 건너뛰고 아이디어 결과를 즉시 표시합니다.
- `api/index.ts`는 Axios 기반 `httpClient`를 제공합니다.
- `store/workspace.ts`에는 현재 `idea`/`analytics` 뷰 값만 있으며 프로젝트 ID나 아이디어 분석 데이터는 없습니다.
- [LangChain 도입 및 적용 가이드](./langchain-adoption-guide.md)에 정리된 대로, 이 프런트엔드 저장소에는 실제 LLM/LangChain 백엔드 구현이 포함되어 있지 않습니다.

### 구현 착수 전 확인이 필요한 의존성

1. 실제 API 서버의 개발 URL과 CORS 설정을 확인해야 합니다.
2. 백엔드 Pydantic 요청/응답 스키마가 [FastAPI 명세](./app-context-fastapi-backend-spec.md)의 JSON 계약과 일치하는지 확인해야 합니다.
3. 인증 쿠키 또는 토큰이 FastAPI 서버에서 검증되는지 확인해야 합니다.
4. 현 `WorkspaceStore`에는 프로젝트 ID가 없습니다. 백엔드가 프로젝트 ID를 필수로 요구하면 프로젝트 상태 연결이 선행되어야 합니다.

아이디어 생성 성공은 FastAPI 응답이 검증된 경우에만 표시됩니다. 백엔드가 실행되지 않거나 오류를 반환하면 성공/더미 결과로 대체하지 않습니다.

## 3. 목표와 범위

### 목표

현재 구현에서는 사용자가 AppContext에 아이디어를 입력하고 Send 버튼을 누르면 다음이 이루어집니다.

1. 입력값을 검증합니다.
2. 첨부된 파일을 업로드하고 서버가 반환한 파일 ID를 저장합니다.
3. `POST /api/v1/idea-generations`에 프롬프트와 파일 ID를 보내 실제 분석 결과를 요청합니다.
4. 참조 소스, 포커스, 아이디어 순으로 skeleton을 표시하고 처리 중 중복 제출을 막습니다.
5. 검증된 아이디어 3개와 포커스를 표시하며, 선택 변경을 백엔드에 저장합니다.
6. 실패 시 toast로 안내하고 프롬프트를 보존합니다.

### 1차 범위

- `Textarea`의 controlled 입력값 관리
- Send 버튼 클릭 제출
- Enter/Shift+Enter 키 동작
- 입력 검증 및 제출 가능 상태
- 진행 중, 성공, 오류 UX
- FastAPI 아이디어 도출 API와 응답 스키마 연동
- 참조 파일 업로드와 파일 ID 전달
- 아이디어 선택 API 연동
- 세 컨텍스트 영역의 순차 skeleton 로딩
- 추천 아이디어 카드 선택
- submit 실패/입력 오류의 toast 표시
- 단위/컴포넌트 테스트

### 1차 범위에서 제외

- 파일 파싱/RAG/vector store 구축 (백엔드 책임)
- 사업계획서 전체 생성 및 분석/채점
- 스트리밍 토큰 출력 및 취소 기능
- 자율 에이전트, 도구 호출, LangGraph 기반 장시간 작업
- 분석 결과의 영구 저장 및 버전 이력 (별도 계약이 준비되지 않은 경우)
- 사업계획서의 모든 더미 텍스트를 AI 응답에 맞춰 재작성

위 제외 항목은 제품 요구와 백엔드 준비도에 따라 별도 범위로 승인합니다.

## 4. 사용자 흐름

```text
아이디어 입력
  → 입력 검증
  → Send 버튼 활성화
  → Send 클릭 또는 Enter
  → 중복 제출 방지 + 진행 상태 표시
  → 참조 소스 skeleton
  → 구조화 포커스 skeleton
  → 아이디어 3개 skeleton
  ├─ API 성공: 아이디어 카드 3개 표시 + 첫 카드 선택
  └─ 오류: toast 표시 + 입력 보존 + 재시도 가능
```

### 상세 시나리오

1. 사용자는 기존 AppContext 패널에서 아이디어를 입력합니다.
2. 입력이 공백뿐이면 Send를 비활성화하거나, 제출 시 입력 안내를 표시합니다.
3. 유효한 입력이 있으면 Send 버튼을 사용할 수 있습니다.
4. 사용자가 Send를 클릭하거나 Enter를 누르면 제출합니다.
5. 제출이 시작되면 Send 버튼을 비활성화하고 각 영역의 skeleton을 순서대로 표시합니다.
6. 입력값은 요청이 성공할 때까지 유지합니다.
7. API 응답 검증에 성공하면 입력값을 지우고 세 개의 제안 카드를 표시합니다. 첫 번째 제안을 기본 선택 상태로 표시합니다.
8. 실패하면 입력값을 지우지 않고 오류 toast를 표시합니다. 사용자는 같은 입력으로 다시 시도할 수 있습니다.

## 5. 입력 및 키보드 동작

### 입력값

| 항목           | 요구사항                                                                                                                                                                                                              |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 값             | 사용자가 입력한 원문 아이디어 문자열                                                                                                                                                                                  |
| 정규화         | 앞뒤 공백을 제거한 값을 서버 요청에 사용합니다. 사용자가 작성한 내부 공백/개행은 보존합니다.                                                                                                                          |
| 비어 있는 값   | trim 결과가 빈 문자열이면 제출하지 않습니다.                                                                                                                                                                          |
| 최대 길이      | 제품/백엔드 제한이 확정되기 전 임의의 UI 최대 길이를 만들지 않습니다. API 계약 확정 시 동일한 제한을 프런트와 백엔드에 적용하고 사용자에게 안내합니다.                                                                |
| 입력 중 변경   | 요청이 진행 중일 때 입력을 잠글지 여부는 UX 선택입니다. 1차 권장안은 제출 중 입력 영역을 잠가 요청과 표시 상태가 어긋나지 않게 하는 것입니다.                                                                         |
| 성공 후 초기화 | 성공적으로 분석을 수신한 뒤 입력을 지울지, 다음 보완 입력을 위해 남길지 결정이 필요합니다. 권장안은 제출한 입력이 결과와 연결된 뒤 입력창을 비우는 것입니다. 다만 결과 확인 경로가 분명하지 않다면 입력을 유지합니다. |

### 키보드

- Enter: 입력이 유효하고 제출 중이 아닐 때 제출합니다.
- Shift+Enter: 줄바꿈을 입력합니다.
- 화면낭독기에서 버튼 이름을 “아이디어 도출” 등 동작을 설명하는 이름으로 제공합니다.
- 한글 IME 조합 입력 중 Enter를 누를 때 조합 완료 이벤트를 제출로 오인하지 않도록 `isComposing`을 확인합니다.
- 버튼 클릭과 Enter는 동일한 submit 함수를 호출해 동작 차이를 만들지 않습니다.

## 6. 버튼과 진행 상태 UX

### Send 버튼

- 현재 아이콘 기반 스타일과 위치를 유지합니다.
- 접근 가능한 이름(`aria-label`)을 제공합니다.
- 입력이 공백뿐이거나 제출 중이면 비활성화합니다.
- 로딩 중에는 아이콘을 진행 표시로 교체하거나 기존 아이콘을 비활성화 상태로 표현합니다. 버튼 크기와 패널 레이아웃은 바꾸지 않습니다.
- 실패 후에는 같은 입력으로 재시도할 수 있게 합니다.

### 상태 정의

| 상태         | 표현                             | 입력/버튼 동작                 |
| ------------ | -------------------------------- | ------------------------------ |
| `idle`       | 기본 입력 화면                   | 유효한 입력이면 제출 가능      |
| `submitting` | 요청 진행 중 안내                | 중복 제출 불가; 입력/버튼 잠금 |
| `success`    | 분석 결과가 전달되었음을 알림    | 분석 결과를 기존 흐름에서 확인 |
| `error`      | 사용자에게 이해 가능한 실패 안내 | 입력 보존; 재시도 가능         |

상태는 컴포넌트 로컬 상태로 시작합니다. 프로젝트 전역에 결과를 공유할 필요가 확인된 경우에만, 도메인 상태를 별도로 설계합니다. 현재 `WorkspaceStore.view`에 분석 결과를 무리하게 섞지 않습니다.

### 오류 메시지

원시 서버 스택 트레이스나 공급자 오류를 그대로 보여주지 않습니다. 사용자 메시지는 오류 종류를 구분합니다.

| 오류 상황               | 사용자 메시지 예시                                                                 |
| ----------------------- | ---------------------------------------------------------------------------------- |
| 입력 누락               | 아이디어를 입력해 주세요.                                                          |
| 로그인 만료             | 로그인이 만료되었습니다. 다시 로그인해 주세요.                                     |
| 권한/프로젝트 접근 실패 | 현재 프로젝트에 접근할 수 없습니다. 프로젝트를 다시 확인해 주세요.                 |
| 네트워크 연결 실패      | 서버에 연결하지 못했습니다. 연결을 확인한 후 다시 시도해 주세요.                   |
| 서버/모델 일시 오류     | 분석을 완료하지 못했습니다. 잠시 후 다시 시도해 주세요.                            |
| 입력 제한 초과          | 입력 가능한 길이를 확인해 주세요. (실제 API 제한이 정해진 경우 구체적인 제한 표시) |

세부 원인과 `requestId`는 개발/서버 로그에 남기되, 비밀 정보나 사용자 문서 원문을 UI 오류로 노출하지 않습니다.

## 7. API 계약 초안

다음 계약은 [LangChain 도입 및 적용 가이드](./langchain-adoption-guide.md)의 초안을 AppContext 단일 아이디어 제출 흐름에 적용한 것입니다. 서버 담당자 확인 후 확정해야 하며, 현재 백엔드에 해당 endpoint가 존재한다고 가정하지 않습니다.

### 요청

```http
POST /api/v1/projects/{projectId}/analyses
Content-Type: application/json
Authorization: 기존 인증 방식
```

```json
{
    "ideaText": "냉장고 속 남은 식재료를 활용해 1인 가구의 식재료 폐기를 줄이는 서비스",
    "referenceDocumentIds": [],
    "requestedSections": ["problem", "solution", "growth", "team"],
    "language": "ko"
}
```

### 계약 규칙

- `projectId`는 현재 선택된 프로젝트의 실제 ID여야 합니다. 화면 제목이나 하드코딩 문자열을 ID로 사용하지 않습니다.
- 프로젝트 ID가 없으면 API 요청을 보내지 않고 프로젝트 선택/생성 흐름을 안내합니다.
- `ideaText`는 trim한 입력값입니다.
- `referenceDocumentIds`는 실제 업로드/등록된 자료의 ID만 전달합니다. 현재 표시 중인 하드코딩 카드 이름을 가짜 문서 ID로 변환하지 않습니다.
- 실제 첨부 자료 기능이 없는 동안에는 빈 배열을 전달하거나 필드를 생략하는 방식 중 하나로 계약을 통일합니다.
- `requestedSections`는 1차로 PSST 4영역을 요청합니다. 서버가 섹션별 결과를 지원하지 않는 경우 단일 결과 스키마를 사용하도록 계약을 조정합니다.
- 모델 공급자 키, 시스템 프롬프트, 임의의 provider/model 선택값을 브라우저에서 보내지 않습니다.

### 성공 응답 초안

```json
{
    "analysisId": "analysis_123",
    "projectId": "project_123",
    "status": "completed",
    "schemaVersion": "1.0",
    "ideaSummary": "남은 식재료를 활용한 레시피 및 장보기 연동 서비스",
    "sections": {
        "problem": {
            "summary": "문제인식 초안",
            "gaps": ["목표 고객 인터뷰 결과가 필요합니다."]
        },
        "solution": {
            "summary": "실현가능성 초안",
            "gaps": []
        },
        "growth": {
            "summary": "성장전략 초안",
            "gaps": ["시장 규모 산출 근거가 필요합니다."]
        },
        "team": {
            "summary": "팀 구성 초안",
            "gaps": []
        }
    },
    "assumptions": ["시장 규모와 매출 목표는 검증되지 않았습니다."]
}
```

응답의 필드/타입은 프런트와 백엔드가 공동으로 정의한 DTO로 고정합니다. 분석 결과 중 일부가 불가능하거나 자료가 없으면 성공 형태의 허위 값 대신 `null`, 빈 배열 또는 `gaps`로 명시합니다.

### 오류 응답 초안

```json
{
    "error": {
        "code": "MODEL_UNAVAILABLE",
        "message": "분석 서비스를 일시적으로 사용할 수 없습니다.",
        "requestId": "req_123"
    }
}
```

프런트엔드는 상태 코드와 안정적인 오류 코드로 사용자 메시지를 결정합니다. 알 수 없는 오류는 일반 오류 안내를 사용하고 실패를 성공 응답 형태로 변환하지 않습니다.

### 동기/비동기 API 선택

1차 구현은 결과가 사용자 대기 허용 시간 안에 안정적으로 끝나는지 측정한 뒤 결정합니다.

- **동기 API:** 한 요청으로 완료 결과를 반환. 구현이 단순하고 초기 PoC에 적합합니다.
- **비동기 API:** `202 Accepted`와 `analysisId`를 먼저 반환한 뒤 상태 조회 또는 이벤트 스트림을 사용. 분석 시간이 길거나 작업 재개가 필요할 때 선택합니다.

백엔드 응답 시간/모델 제한을 측정하기 전에는 스트리밍이나 비동기 작업을 선결정하지 않습니다. 1차 범위는 동기 계약을 기본으로 하되, 응답 시간이 기준을 초과하면 비동기로 전환합니다.

## 8. 프런트엔드 설계 제안

### API 모듈

기존 `api/auth.ts` 등 도메인 모듈 패턴에 맞춰 다음을 추가하는 방향을 제안합니다.

```text
api/
  idea-analysis.ts       # API 요청 함수와 요청/응답 타입 import
types/
  idea-analysis.ts       # API DTO 타입
```

구현 시 API 모듈은 `httpClient`를 사용하고, UI 컴포넌트에서 Axios endpoint나 응답 파싱을 직접 작성하지 않습니다.

### 상태 소유권

1차 제출 상태(`input`, `status`, `error`)는 `AppContext`의 컴포넌트 로컬 상태가 적절합니다.

성공 응답의 전달 위치는 다음 중 기존 프로젝트 구조와 가장 잘 맞는 곳으로 결정합니다.

1. 선택 프로젝트 상세 상태가 이미 있다면 해당 프로젝트 상태/쿼리 캐시를 갱신합니다.
2. 앱 내 여러 탭이 즉시 같은 결과를 사용해야 한다면 분석 결과 전용 도메인 스토어를 검토합니다.
3. 영구 저장 API가 준비되지 않았다면 일시적으로 상위 워크스페이스 상태에 전달하되, 새로고침 후 유지된다고 표현하지 않습니다.

현재 `WorkspaceStore`는 화면 뷰만 관리하므로 분석 결과 저장소라고 간주하지 않습니다. 결과 데이터의 소유자는 구현 전에 결정합니다.

### 결과 표시 연결

Send 성공 후 어디에 결과를 표시할지 명확한 제품 동작이 필요합니다. 본 명세의 권장 동작은 **응답을 분석 결과로 보존하고 기존 아이디어 구조화 흐름에서 즉시 확인할 수 있도록 연결**하는 것입니다. 기존 분석 화면의 정적 더미 점수/카드를 자동으로 실제 결과처럼 바꾸는 것은 응답 스키마와 UI 매핑을 함께 확정한 후 별도 작업으로 진행합니다.

## 9. 접근성 및 사용성

- 입력에 label 또는 접근 가능한 설명을 제공하고 placeholder만 label로 대체하지 않습니다.
- Send 버튼에 `aria-label` 또는 텍스트 이름을 제공합니다.
- 진행/성공/오류 메시지는 적절한 `aria-live` 영역에서 전달합니다.
- 키보드만으로 입력과 전송이 가능합니다.
- 비활성 버튼은 색상만으로 이유를 추측하게 하지 않고 입력 안내를 제공합니다.
- 오류 발생 시 입력 내용은 보존하고, 가능하면 입력란 또는 오류 메시지로 포커스를 이동합니다.
- 분석 완료 사실과 결과를 확인할 위치를 명확히 알립니다.

## 10. 보안 및 신뢰성 요구사항

- LangChain 및 모델 제공자 호출은 백엔드에서만 수행합니다.
- 프런트에서 보낸 `projectId`/문서 ID의 권한 검증을 백엔드가 수행합니다.
- 브라우저에서 임의로 전달한 사용자 ID를 신뢰하지 않습니다.
- 입력 길이와 요청 빈도를 서버에서 제한합니다.
- 사용자 입력은 모델에 전달되는 데이터이며 지시문으로 무조건 신뢰하지 않습니다.
- 모델 응답은 API 응답 전에 서버에서 스키마 검증합니다.
- 공급자 키, 프롬프트 내부 비밀 값, 인증 정보는 클라이언트에 노출하지 않습니다.
- 중복 클릭/키 입력으로 인한 중복 요청과 비용을 방지합니다.
- 네트워크/모델 오류를 성공 결과나 정적 더미 결과로 숨기지 않습니다.
- 로깅 시 아이디어 원문 저장 필요성, 개인정보 여부, 보존 기간을 결정합니다.

## 11. 테스트 계획

### 단위 테스트

- trim 후 빈 입력을 제출하지 않음
- 유효 입력을 요청 DTO로 올바르게 변환
- 프로젝트 ID 누락 시 API를 호출하지 않음
- 응답 상태 코드/오류 코드에 맞는 사용자 오류 표시
- 한글 IME 조합 중 Enter는 제출하지 않음

### 컴포넌트 테스트

- 초기 상태에서 기존 UI가 유지됨
- 입력 후 Send 버튼 활성화
- 버튼 클릭으로 한 번만 제출
- Enter 제출, Shift+Enter 개행
- 제출 중 버튼 재클릭/Enter 중복 제출 방지
- 진행 상태 표시
- 성공 후 분석 결과 전달 및 합의된 입력 초기화 동작
- 오류 후 입력 보존 및 재시도

### API/통합 테스트

- `httpClient`를 통한 endpoint와 DTO 확인
- 401/403/404/429/5xx 및 네트워크 오류 처리
- 유효하지 않은 응답 스키마는 성공으로 처리하지 않음
- 권한 없는 프로젝트 ID를 백엔드에서 거부
- 실제 모델 키 없이 mock으로 프런트/백엔드 계약 테스트

테스트는 실제 모델 호출에 의존하지 않도록 기본적으로 mock/fake 공급자를 사용합니다. 실제 모델 스모크 테스트는 별도 제한된 환경과 비용 한도로만 실행합니다.

## 12. 완료 기준 (Acceptance Criteria)

### 프런트엔드 통합 검수 기준

1. 공백뿐인 입력은 API로 전달되지 않고 toast 안내가 표시됩니다.
2. 정상 아이디어 입력은 Send 클릭으로 한 번만 생성 API에 전달됩니다.
3. 키보드 Enter 제출이 지원되고 Shift+Enter는 줄바꿈으로 동작합니다.
4. 한글 IME 조합 중 Enter가 중복 제출을 일으키지 않습니다.
5. 참조 소스 → 포커스 레이어 → 아이디어 카드 순으로 skeleton 상태가 노출됩니다.
6. API 성공 시 검증된 제안 카드 3개가 표시됩니다.
7. 첫 아이디어가 기본 선택되고, 선택 변경은 selection API 성공 후 반영됩니다.
8. 처리 중 중복 요청이 발생하지 않고 진행 상태가 보입니다.
9. 예외가 발생하면 입력을 보존하고 오류 toast를 표시합니다.
10. 빈 입력 오류와 성공 안내 역시 공통 toast UI로 표시됩니다.
11. Context 패널의 콘텐츠가 잘리지 않고 내부 스크롤로 확인할 수 있습니다.
12. 기존 화면의 주요 레이아웃과 사업계획서 탭이 보존됩니다.
13. 타입 검사, 빌드 및 관련 테스트가 통과합니다.

### 백엔드 API 연동 후 추가 기준

- 요청에 정규화된 아이디어와 실제 업로드 파일 ID가 포함됩니다. 현재 구현은 아직 프로젝트 상태에 프로젝트 ID가 없어 `project_id: null`을 보냅니다.
- 백엔드가 프로젝트 ID를 필수로 요구하면 실제 프로젝트 식별자 상태 연결이 선행되어야 합니다.
- 성공 응답은 정의된 타입/스키마를 따르고 분석 결과 흐름에 전달됩니다.
- 서버/네트워크 오류 시 입력을 보존하고 재시도할 수 있습니다.
- 모델 API 키와 LangChain 호출은 브라우저 번들에 포함되지 않습니다.

## 13. 구현 단계 제안

### 후속 단계 1: 계약/환경 검증

- FastAPI의 실제 Pydantic 스키마가 프런트엔드 계약과 일치하는지 확인합니다.
- 개발 API URL, CORS, 인증 쿠키/토큰을 확인합니다.
- 프로젝트 ID를 백엔드가 필수로 요구하는지 확인하고 필요하면 프런트 상태를 연결합니다.

### 완료된 현재 단계: FastAPI API 프런트엔드 연동

- 파일 업로드, 아이디어 생성 및 아이디어 선택 API 호출을 연결합니다.
- 세 영역의 순차 skeleton, 입력 검증, toast 피드백을 유지합니다.
- 실제 백엔드 동작 검증은 백엔드 URL과 FastAPI 서버 실행 환경이 준비되어야 합니다.

### 후속 단계 2: 백엔드 분석 API 검증

- 인증/프로젝트 권한 검증, 요청 스키마, 제한이 백엔드에서 적용되는지 검증합니다.
- 백엔드의 모델 호출과 출력 검증을 API 계약 테스트로 확인합니다.
- 비용/지연 시간/실패를 계측하고 에러 계약에 맞춰 반환하는지 확인합니다.

### 후속 단계 3: 사업계획서 결과 연결 및 평가

- 아이디어 도출 응답을 기존 사업계획서/분석 화면의 데이터 모델로 매핑합니다.
- 실제 결과와 정적 더미 표시를 명확히 구분합니다.
- 골든셋, 실패 처리, 회귀 테스트를 추가합니다.

| 실패 후 재시도 | 입력 보존, 사용자가 재시도             | 실패를 성공 결과로 감추지 않기 위함입니다.                    |
| 결과 영구 저장 | API/DB 준비 시 함께 정의               | 현재 저장 스키마를 확인할 수 없습니다.                        |

## 15. 첫 구현 PR에서 권장하는 범위

계약 승인 후 첫 PR은 다음 범위로 제한합니다.

1. `api/idea-analysis.ts`에 합의한 요청 함수와 타입 연결
2. `AppContext`에서 입력값, 제출 상태, 오류 상태 관리
3. Send 버튼 클릭과 Enter/Shift+Enter 동작
4. 프로젝트 ID 유무 검사 및 API 요청
5. 요청 mock을 이용한 성공·실패 컴포넌트 테스트
6. 성공 결과를 어느 화면/스토어로 전달할지 최소 연결
7. 기존 입력 패널 디자인과 분석/보고서 레이아웃 보존
