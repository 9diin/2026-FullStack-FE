# AppContext 아이디어 도출 FastAPI 백엔드 기능 명세서

## 1. 문서 목적

이 문서는 프런트엔드 `AppContext`에서 입력한 사업 아이디어 프롬프트를 FastAPI 백엔드로 전달하고, 백엔드가 참조 파일을 확인·분석한 뒤 구조화된 추천 아이디어 3개를 반환하는 기능의 백엔드 구현 기준을 정의합니다.

기능 구현자는 이 문서를 기준으로 API 계약, 입력 검증, 인증·인가, 파일 처리, LLM 연동, 응답 검증 및 오류 처리를 구현할 수 있습니다. 실제 모델 제공자, 데이터베이스, 인증 방식, 프로젝트 도메인 등 아직 결정되지 않은 항목은 **구현 전 결정 사항**으로 표시합니다.

## 2. 현재 프런트엔드 기준 동작

현재 연결 대상은 [AppContext](../components/common/app-context.tsx)입니다.

- 사용자는 Textarea에 아이디어 또는 해결하고 싶은 문제를 입력하고 Send 버튼 또는 Enter로 제출합니다. Shift+Enter는 줄바꿈입니다.
- 입력 중에는 안내 문구가 유지됩니다. 입력만으로 컨텍스트 영역을 표시하지 않습니다.
- 유효한 프롬프트가 제출되면 요청 처리 중 참조 소스 컨텍스트, 구조화 포커스 레이어, 핵심 분석 아이디어 영역이 나타납니다.
- 처리 중에는 참조 소스 → 포커스 → 아이디어 순으로 각 영역의 skeleton을 표시합니다. 이 진행 표시는 프런트엔드 UX이며, 백엔드에서 의도적으로 대기하거나 인위적인 지연을 추가하지 않습니다.
- 실제 응답을 받기 전까지 성공 결과처럼 보이는 더미 추천 아이디어를 표시하지 않습니다.
- 성공 시 아이디어 3개를 카드로 표시하고, 기본으로 첫 번째 카드를 선택합니다. 사용자가 다른 카드를 선택할 수 있습니다.
- 오류 시 입력값은 보존하고 전역 toast로 알립니다. 오류를 빈 결과나 임의의 성공 응답으로 바꾸지 않습니다.
- 참조 파일이 없으면 파일명을 만들어 표시하지 않고 “참조할 파일이 없습니다” 상태를 표시합니다. 현재 빈 상태 영역은 파일 카드 3개와 비슷한 높이를 유지합니다.
- 파일이 첨부된 경우에만 백엔드가 확인한 실제 파일명과 파일 수를 표시합니다.

### 현재 구현상 제약

- 프런트엔드는 `api/idea-generation.ts`를 통해 아이디어 생성, 참조 파일 업로드, 아이디어 선택 API를 호출합니다.
- 파일 선택/업로드 흐름이 연결되어 있으며, 업로드 성공 응답의 파일 ID를 아이디어 도출 요청에 포함합니다.
- 현재 워크스페이스 상태에는 프로젝트 ID가 없습니다. 프로젝트별 소유권을 API에 적용하려면 프런트엔드가 프로젝트 식별자를 확보하는 경로를 먼저 정해야 합니다.
- 생성 요청은 현재 `project_id: null`을 전달합니다. 백엔드 스키마가 `project_id`를 받지 않는 경우 이 필드를 생략하도록 프런트 API 모듈을 조정해야 합니다.

## 3. 목표와 범위

### 3.1 목표

1. 프롬프트와 선택적으로 첨부한 참조 파일 ID를 받아 분석합니다.
2. 업로드 파일을 요청 사용자 및 프로젝트 권한 기준으로 검증하고, 권한이 확인된 문서만 분석에 사용합니다.
3. 문제 해결 관점이 서로 다른 추천 아이디어를 정확히 3개 반환합니다.
4. 각 추천 아이디어에 제목과 구체적인 설명 항목을 포함합니다.
5. 참조 파일 메타데이터와 구조화 포커스 항목을 응답해 프런트엔드가 실제 컨텍스트를 표시할 수 있게 합니다.
6. 모델의 자유 형식 출력을 검증한 뒤에만 API 응답으로 전달합니다.
7. 오류를 명확한 HTTP 상태 코드와 안정된 오류 본문으로 전달합니다.

### 3.2 이번 기능의 범위

- 아이디어 도출 API
- 요청/응답 Pydantic 스키마 및 입력 검증
- 인증된 사용자의 파일 접근 권한 검증
- 선택 파일의 텍스트 추출 또는 기존 문서 처리 파이프라인 재사용
- LLM 결과 구조화 및 스키마 검증
- 프런트엔드에 실제 파일명, 분석 포커스, 추천 아이디어 반환
- 적절한 오류 응답, 로그 및 테스트

### 3.3 범위 제외 또는 후속 결정

- 사업계획서 전체(문제인식·실현가능성·성장전략·팀구성) 생성
- TAM/SAM/SOM, 재무 예측, 예산 또는 정부지원금 규모 산출
- 심사 점수 및 “합격 가능성” 산출
- 보고서 저장, 이력 관리, 재생성 버전 관리
- 모델 공급자, 모델명, 임베딩 모델의 구체적인 선택
- 비동기 작업 큐, SSE/WebSocket 스트리밍

위 항목은 별도 요구사항과 근거 데이터 계약 없이 이번 API에 섞지 않습니다. 특히 근거가 없는 시장/재무 수치나 평가 점수를 사실처럼 생성하지 않습니다.

## 4. 권장 아키텍처와 처리 흐름

```text
Next.js AppContext
  ├─ (선택) 파일 업로드 API로 파일 업로드 → source_file_id 확보
  └─ 아이디어 도출 API에 prompt + source_file_ids 제출
       ↓
FastAPI Router
  ├─ 인증 및 사용자 식별
  ├─ 요청 스키마/길이/개수 검증
  ├─ 파일 소유자·프로젝트·처리상태 검증
  └─ IdeaGenerationService 호출
       ↓
애플리케이션 서비스
  ├─ 프롬프트 정규화
  ├─ 권한이 검증된 파일 콘텐츠 조회 (파일이 있을 때만)
  ├─ 분석 포커스 도출
  ├─ LLM 호출 (선택된 Python LangChain 어댑터 또는 직접 클라이언트)
  ├─ Pydantic 결과 검증 및 의미 검증
  └─ 검증된 API 응답 반환
```

권장 책임 분리 예:

```text
app/
  api/v1/idea_generations.py       # HTTP 라우트/상태 코드
  schemas/idea_generation.py       # 요청·응답 Pydantic 모델
  services/idea_generation.py      # 애플리케이션 흐름과 검증
  repositories/source_files.py    # 소유권이 확인된 파일 조회
  llm/idea_generator.py            # LLM 제공자/LangChain 어댑터
  core/errors.py                   # 공통 오류 계약
```

기존 백엔드 구조가 있다면 해당 구조를 우선 따르고, 이 예시 경로를 그대로 강제하지 않습니다. 라우터에 프롬프트 조립, DB 조회, 공급자 SDK 호출, 결과 변환을 한꺼번에 넣지 않습니다.

### 동기 요청 권장

첫 버전은 단일 동기 JSON 요청/응답을 권장합니다. 백엔드 응답 완료 시점에 검증된 결과를 한 번에 반환하고, 프런트엔드는 처리 중인 동안 단계별 skeleton을 표시합니다.

- 백엔드는 3초 sleep 또는 UI 표시 시간을 맞추기 위한 지연을 추가하지 않습니다.
- 프런트엔드는 응답을 기다리는 동안 skeleton을 표시하고, 응답 도착 즉시 결과를 표시합니다.
- 실제 LLM 호출이 동기 요청 제한 시간을 지속적으로 넘거나 작업 재개/취소가 필요해지면 별도 비동기 job API를 설계합니다. 최초 구현부터 polling/SSE를 임의로 추가하지 않습니다.

## 5. API 계약

### 5.1 아이디어 도출

```http
POST /api/v1/idea-generations
Content-Type: application/json
Authorization: Bearer <access-token>
```

#### 요청 예시

```json
{
    "prompt": "1인 가구의 식재료 낭비를 줄일 수 있는 서비스를 만들고 싶어요.",
    "source_file_ids": ["4bc61393-e8cb-43d8-8c49-cde51e8717ae"],
    "project_id": null
}
```

#### 요청 필드

| 필드              | 타입           |   필수 | 규칙                                                                                                                                                                                                  |
| ----------------- | -------------- | -----: | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `prompt`          | string         |     예 | trim 이후 공백이 아니어야 합니다. 권장 최대 길이 5,000자. 프런트엔드/백엔드 모두 검증합니다.                                                                                                          |
| `source_file_ids` | UUID 배열      | 아니오 | 기본값 `[]`. 중복 ID 금지. 권장 최대 10개. 모든 파일은 인증 사용자(및 프로젝트가 적용되면 해당 프로젝트)에 속해야 하고 분석 가능한 상태여야 합니다.                                                   |
| `project_id`      | UUID 또는 null | 미결정 | 현재 프런트엔드에 프로젝트 ID가 없습니다. 프로젝트 단위 데이터 모델/권한이 정해지기 전에는 `null` 또는 생략을 허용합니다. 프로젝트가 필수 도메인이면 프런트 상태/라우팅부터 연결한 다음 필수화합니다. |

### 5.2 파일 업로드 전제 및 권장 계약

현재 AppContext에는 실제 업로드 연결이 없습니다. 파일 이름을 응답에 표시하려면 프런트엔드가 신뢰 가능한 서버 파일 ID를 받아야 합니다. 권장 흐름은 다음과 같습니다.

1. 사용자가 파일을 선택합니다.
2. 프런트엔드가 `POST /api/v1/source-files`로 파일을 업로드합니다.
3. 서버가 파일 형식/크기/사용자 권한을 검증하고 `source_file_id`, 실제 저장 파일명, 처리 상태를 반환합니다.
4. AppContext가 업로드 완료된 파일을 보이고, 아이디어 도출 요청에 `source_file_ids`를 포함합니다.
5. 도출 API는 각 파일 ID의 소유권과 처리 상태를 다시 검증하고, 확인된 파일만 컨텍스트에 사용합니다.

업로드 계약은 기존 백엔드 파일 API가 있으면 재사용합니다. 없다면 별도 계약을 정합니다. 제안 endpoint:

```http
POST /api/v1/source-files
Content-Type: multipart/form-data
Authorization: Bearer <access-token>
```

응답은 최소한 아래 정보를 제공해야 합니다.

```json
{
    "id": "4bc61393-e8cb-43d8-8c49-cde51e8717ae",
    "filename": "시장 인터뷰 요약.pdf",
    "media_type": "application/pdf",
    "size_bytes": 152340,
    "status": "ready"
}
```

권장 초기 허용 형식/크기:

- PDF, DOCX, TXT, XLSX 등 실제 텍스트 추출을 지원하는 형식만 허용합니다.
- 허용 확장자 목록과 MIME 검증을 함께 적용합니다. 확장자만 신뢰하지 않습니다.
- 파일당 최대 크기는 운영 환경에 맞춰 설정합니다. 기본 제안은 20 MiB이며, 제품/인프라 결정 후 고정합니다.
- 업로드 후 문서 추출이 끝나기 전에는 `processing` 상태로 반환할 수 있습니다. 도출 API는 `ready`가 아닌 파일을 명확한 오류로 거절합니다.
- 악성 파일 검사, 저장소 암호화/수명, 파일 삭제 정책은 서비스 보안 정책에 맞춥니다.
- 파일명은 UI 표시용 메타데이터로 취급하며 경로/저장 키로 사용하지 않습니다.

## 6. 입력 검증 및 도메인 규칙

### 프롬프트

- 앞뒤 공백을 제거한 값을 분석에 사용합니다.
- 빈 문자열은 `422`로 거절합니다.
- 권장 최소 길이는 2자, 최대 길이는 5,000자입니다. 실제 제품 제한은 프런트엔드와 일치시킵니다.
- HTML/Markdown을 실행하거나 렌더링 가능한 코드로 취급하지 않습니다.
- 프롬프트 안의 지시문이 시스템/개발자 지침, 비공개 프롬프트, 타 사용자 자료를 노출하도록 요구하더라도 이를 따르지 않도록 모델 지침을 구성합니다.

### 파일

- 파일 ID는 서버가 발급한 식별자만 허용합니다.
- 파일 접근 검증은 요청 사용자의 인증 정보로 수행합니다. 파일명/ID를 안다는 이유만으로 접근을 허용하지 않습니다.
- 다른 사용자 또는 권한 없는 프로젝트의 파일 ID는 콘텐츠를 조회하거나 존재 여부를 과도하게 노출하지 않습니다.
- 삭제/실패/처리 중 파일은 분석에 사용할 수 없습니다.
- 참조 파일이 없으면 빈 파일 목록 그대로 분석하고 응답의 `source_files`도 `[]`로 반환합니다. 임의의 파일명이나 근거를 만들지 않습니다.
- 파일 텍스트는 비신뢰 입력입니다. 문서 안의 prompt injection이 시스템 정책을 변경하지 못하도록 분리하고, 자료의 내용은 근거로만 취급합니다.

### 결과

- 정확히 3개의 추천 아이디어를 반환해야 합니다. 3개를 만들 수 없거나 결과가 구조 검증을 통과하지 못하면 오류로 처리합니다.
- 세 아이디어는 같은 표현을 바꾼 중복이 아니라 서로 다른 해결 방향을 제시해야 합니다.
- 각 카드 설명은 짧고 UI에 적합한 문장으로 작성하며, 실행 가능한 근거가 없으면 확정적 사실이나 수치를 단정하지 않습니다.
- 결과는 JSON 스키마 검증 및 의미 검증 후 반환합니다.
- LLM 원문, 내부 chain trace, API 키, 전체 프롬프트 템플릿은 클라이언트 응답에 포함하지 않습니다.

## 7. 오류 응답 계약

모든 오류는 성공 데이터처럼 위장하지 않습니다. 공통 오류 형식을 권장합니다.

```json
{
    "error": {
        "code": "SOURCE_FILE_NOT_READY",
        "message": "아직 분석할 수 없는 참조 파일이 포함되어 있습니다.",
        "request_id": "req-7f127d8f"
    }
}
```

|  HTTP | `code` 예시                                                   | 사용 상황                            | 프런트엔드 동작                                       |
| ----: | ------------------------------------------------------------- | ------------------------------------ | ----------------------------------------------------- |
| `400` | `INVALID_REQUEST`                                             | JSON/요청 형식 오류                  | 일반 오류 toast                                       |
| `401` | `UNAUTHENTICATED`                                             | 로그인/토큰 없음 또는 만료           | 기존 인증 흐름 처리                                   |
| `403` | `FORBIDDEN`                                                   | 프로젝트 기능 사용 권한 없음         | 권한 오류 안내                                        |
| `404` | `SOURCE_FILE_NOT_FOUND`                                       | 요청 파일을 찾을 수 없음             | 파일 상태 새로고침 또는 오류 안내                     |
| `413` | `FILE_TOO_LARGE`                                              | 업로드 파일 크기 제한 초과           | 허용 크기를 명시해 안내                               |
| `415` | `UNSUPPORTED_FILE_TYPE`                                       | 지원하지 않는 파일 형식              | 지원 형식 안내                                        |
| `422` | `PROMPT_REQUIRED`, `PROMPT_TOO_LONG`, `SOURCE_FILE_NOT_READY` | 의미/상태 검증 실패                  | 서버 메시지를 안전하게 표시하거나 일반 입력 오류 안내 |
| `429` | `RATE_LIMITED`                                                | 사용자/프로젝트 요청 제한 초과       | 재시도 대기 안내                                      |
| `502` | `LLM_INVALID_RESPONSE`                                        | 모델 응답 파싱 또는 스키마 검증 실패 | 실패 toast, 입력 보존                                 |
| `503` | `LLM_UNAVAILABLE`                                             | 공급자 장애/점검                     | 잠시 후 재시도 안내                                   |
| `504` | `GENERATION_TIMEOUT`                                          | 모델 응답 시간 초과                  | 재시도 안내, 서버의 요청 ID 보존                      |
| `500` | `INTERNAL_ERROR`                                              | 예상하지 못한 내부 오류              | 일반 실패 toast, 세부정보는 서버 로그에서만 확인      |

오류의 `message`에 공급자 원문, 프롬프트, 파일 내용, stack trace, 내부 URL 또는 비밀 값을 넣지 않습니다. 로그에는 `request_id`를 포함하고 민감 콘텐츠를 기록하지 않습니다.

## 8. 인증, 권한, 개인정보 및 운영 안전성

- 모든 생성/업로드 요청은 인증이 필요합니다. 인증 방식은 기존 백엔드의 세션/JWT 계약을 따릅니다.
- 프로젝트 ID가 도입되면 사용자의 프로젝트 소속/역할을 먼저 확인하고, 동일 권한 범위 안에서만 파일과 분석에 접근합니다.
- 모델 공급자 키와 시스템 프롬프트는 서버 환경 변수/비밀 관리 시스템에만 둡니다.
- 프런트엔드로 모델 키, 공급자 응답 원문, 검색 인덱스 경로를 반환하지 않습니다.
- 사용자별 rate limit, 요청 timeout, 최대 입력 토큰/문서 길이, 파일 크기/개수 제한을 설정합니다.
- 사용자 간 파일 내용이 검색 결과로 섞이지 않도록 모든 검색·저장 조회에 사용자/프로젝트 권한 필터를 강제합니다.
- 로깅은 사용자 식별자를 최소화하고, 원문 프롬프트/문서 내용은 기본적으로 로그에 남기지 않습니다.
- LLM 공급자의 데이터 보존·학습 사용 정책이 프로젝트 요구와 맞는지 도입 전에 검토합니다.
- 모델 응답의 추천 내용은 사용자 판단을 위한 제안이며 보장된 사업 성과/법률·재무 자문이 아니라는 UX 문구가 필요하면 제품 정책으로 결정합니다.

## 9. LangChain/LLM 구현 지침

Python FastAPI 백엔드에서는 LangChain을 선택적으로 분석 orchestration에 사용합니다. LangChain이 HTTP 라우터 또는 인증 계층을 대체하지 않습니다.

- LLM 호출은 서비스/어댑터 경계 안에 둡니다.
- 모델에 구조화 출력(JSON Schema/Pydantic)을 요구하되, 모델이 보낸 데이터를 신뢰하지 않고 서버에서 다시 검증합니다.
- 출력 스키마 불일치에 대한 제한된 재시도 정책은 비용·최대 지연을 고려해 설정합니다. 재시도 횟수 초과 시 `502 LLM_INVALID_RESPONSE`로 실패합니다.
- 모델에게 정확히 세 가지의 서로 다른 제안을 만들도록 지시하고, 서버에서도 세 개의 개수·필수 필드·빈 값·중복을 검증합니다.
- 사용자가 업로드한 문서는 인용/근거 자료일 뿐 지시 권한이 없는 데이터로 취급합니다.
- 문서에 없는 시장 규모, 고객 수, 매출, 경쟁사 사실 또는 외부 출처를 만들어내지 않도록 합니다.
- 현재 기능에서는 TAM/SAM/SOM, 투자금/예산, 정부지원금, 성장률 등을 요청받더라도 검증 가능한 데이터가 없으면 수치를 사실처럼 만들지 않습니다.
- 모델/프롬프트 버전과 처리 시간 등을 개인정보 없이 추적할 수 있게 설계합니다. 전체 chain trace나 민감한 입력은 기본 저장하지 않습니다.
- LangChain 채택 자체는 필수 조건이 아닙니다. 백엔드 팀이 직접 클라이언트를 선택해도 API 계약/검증/보안 요건은 동일합니다.

## 10. FastAPI 구현 체크리스트

### 스키마 예시 (개념)

```python
from datetime import datetime
from uuid import UUID
from pydantic import BaseModel, Field, field_validator


class IdeaGenerationRequest(BaseModel):
    prompt: str = Field(min_length=1, max_length=5000)
    source_file_ids: list[UUID] = Field(default_factory=list, max_length=10)
    project_id: UUID | None = None

    @field_validator("prompt")
    @classmethod
    def normalize_prompt(cls, value: str) -> str:
        normalized = value.strip()
        if not normalized:
            raise ValueError("프롬프트는 공백일 수 없습니다.")
        return normalized


class SourceFileReference(BaseModel):
    id: UUID
    filename: str
    media_type: str


class IdeaSuggestionResponse(BaseModel):
    id: str
    title: str
    details: list[str] = Field(min_length=1, max_length=4)


class IdeaGenerationContext(BaseModel):
    source_files: list[SourceFileReference]
    focus_items: list[str] = Field(min_length=1, max_length=8)


class IdeaGenerationResponse(BaseModel):
    generation_id: UUID
    created_at: datetime
    context: IdeaGenerationContext
    suggestions: list[IdeaSuggestionResponse] = Field(min_length=3, max_length=3)
```

예시는 계약의 형태를 설명하는 용도입니다. 설치된 Pydantic/FastAPI 버전, 공통 베이스 모델, 기존 오류 처리 방식에 맞춰 구현합니다. Pydantic 모델만으로는 아이디어 ID 중복이나 의미상 중복까지 검증할 수 없으므로 서비스 계층에서 추가 확인합니다.

### 라우트 동작

1. 인증 principal에서 사용자 ID를 얻습니다. body의 사용자 ID를 신뢰하지 않습니다.
2. prompt 길이, 파일 ID 개수/중복을 검증합니다.
3. 프로젝트가 주어진 경우 사용자 접근 권한을 확인합니다.
4. 파일 ID가 있으면 일괄 조회해 누락, 소유자 불일치, 프로젝트 불일치, 처리 미완료를 검증합니다.
5. 파일 ID가 없으면 파일 검색을 호출하지 않습니다.
6. 생성 서비스가 구조화된 결과를 만들고 출력 계약을 검증합니다.
7. 응답의 파일 목록은 권한을 확인한 파일 메타데이터에서 구성합니다.
8. 각 오류는 공통 오류 핸들러로 정규화하고 request ID와 함께 응답합니다.

### 저장 여부

첫 버전에서 분석 결과를 DB에 저장할지는 현재 정보만으로 확정할 수 없습니다.

- 저장하지 않는다면 `generation_id`는 추적용 ID로만 발급하고 결과 보존 정책을 문서화합니다.
- 저장한다면 사용자/프로젝트 소유권, 프롬프트·응답의 보존/삭제, 모델 버전, 파일 참조 수명을 함께 설계합니다.
- `generation_id`를 받는 `GET` 조회 API는 저장 및 이력 기능이 확정된 뒤에 추가합니다.

## 11. 프런트엔드 연동 계약

백엔드 구현 완료 후 프런트엔드는 아래와 같이 연결합니다.

1. `api/idea-generation.ts`에서 `POST /api/v1/idea-generations`를 호출합니다.
2. 요청에 trim한 `prompt`와 업로드 완료된 `source_file_ids`를 보냅니다. 파일이 없으면 `[]`를 보냅니다.
3. 프로젝트 ID를 실제로 확보하기 전까지는 `project_id`를 임의로 만들지 않습니다.
4. `isSubmitting`은 요청 시작부터 성공/실패까지 유지하고 중복 제출을 막습니다.
5. 로딩 중 skeleton은 프런트엔드에서 순차 노출합니다. 요청이 오래 걸려도 마지막 아이디어 skeleton 상태를 유지하고, API 응답 수신 시 결과를 표시합니다.
6. 응답의 `context.source_files`를 참조 소스 카드에 연결합니다. 배열이 비면 “참조할 파일이 없습니다”와 파일 카드 3개에 준하는 빈 상태를 유지합니다.
7. 응답의 `context.focus_items`를 포커스 배지에 연결합니다. 기존 고정 배지 대신 해당 요청 결과를 표시합니다.
8. 응답의 `suggestions`를 카드에 연결하고, 성공 응답 검증 실패는 오류로 처리합니다.
9. 성공한 뒤에만 입력값을 초기화합니다. 실패하면 입력과 첨부 파일 선택 상태를 보존합니다.
10. API의 안전한 사용자 메시지를 toast에 표시합니다. 예상치 못한 내부 정보는 UI에 노출하지 않습니다.
11. 아이디어 선택 시 `POST /api/v1/idea-generations/{generation_id}/selection`에 `selected_idea_id`를 보내며, 성공 후에만 선택 표시를 갱신합니다.

### 11.1 아이디어 선택 저장

카드 선택 시 프런트엔드는 아래 계약으로 선택 API를 호출합니다.

```http
POST /api/v1/idea-generations/{generation_id}/selection
Content-Type: application/json
```

```json
{
    "selected_idea_id": "idea-uuid-2"
}
```

선택 응답 본문은 UI에서 사용하지 않으며, 2xx 성공 후에만 선택 강조를 변경합니다. 오류가 발생하면 기존 선택을 유지하고 toast로 알립니다.

프런트엔드 타입 예:

```ts
export interface IdeaGenerationRequest {
    prompt: string
    source_file_ids: string[]
    project_id?: string | null
}

export interface IdeaSuggestion {
    id: string
    title: string
    details: string[]
}

export interface IdeaGenerationResponse {
    generation_id: string
    created_at: string
    context: {
        source_files: Array<{
            id: string
            filename: string
            media_type: string
        }>
        focus_items: string[]
    }
    suggestions: IdeaSuggestion[]
}
```

프런트엔드 타입은 이 JSON 계약과 일치해야 하며, snake_case/camelCase 변환을 양쪽에서 중복 적용하지 않도록 API 경계에서 규칙을 정합니다.

## 12. 테스트 요구사항

### 단위 테스트

- prompt 앞뒤 공백 정규화
- 공백 입력, 길이 초과, source file 개수 초과/중복 거절
- 파일이 없는 요청에서 파일 조회기를 호출하지 않음
- 접근 권한 없는 파일 ID가 분석에 사용되지 않음
- `ready`가 아닌 파일을 명확히 거절
- 정상 모델 결과가 정확히 세 개의 서로 다른 제안과 구조화된 응답으로 변환됨
- 잘못된 JSON, 필수 필드 누락, 빈 title/details, 아이디어 개수 오류 처리
- 모델 timeout/공급자 오류가 계약된 오류 코드로 변환됨
- 오류 경로에서 가짜 성공 데이터를 반환하지 않음

### API 통합 테스트

- 인증된 유효 요청 및 파일 없음 응답 (`source_files: []`)
- 인증된 유효 요청 및 사용자 소유 파일 응답 (실제 파일명 반환)
- 미인증 요청 `401`
- 다른 사용자 파일 접근 시 거절
- 프로젝트 권한 없음 `403`
- 누락/처리 중 파일 ID에 대한 일관된 오류
- LLM 호출 mock을 이용한 안정된 계약 테스트
- 오류 본문에 stack trace, 프롬프트 원문, 파일 내용, 공급자 키가 포함되지 않음

### 프런트엔드 연동 검수

- Textarea 입력만으로 컨텍스트가 나타나지 않음
- Send 제출 직후 skeleton과 진행 상태가 나타남
- 참조 파일이 없으면 파일명 더미 없이 빈 상태가 나타남
- 실제 업로드 파일이 제출되면 서버가 확인한 파일명만 표시됨
- 결과 응답 도착 전에는 추천 카드가 나타나지 않음
- 정상 응답은 카드 3개와 포커스 항목을 표시하고 첫 카드를 기본 선택함
- 오류는 toast로 나타나며 프롬프트/첨부 상태가 보존됨
- 처리 중 Send 중복 요청이 발생하지 않음
- Enter 제출, Shift+Enter 줄바꿈, 한글 IME 조합 동작이 유지됨

## 13. 완료 기준 (Acceptance Criteria)

- [ ] 인증된 사용자가 AppContext 프롬프트로 생성 API를 호출할 수 있다.
- [ ] 요청 및 응답 계약이 OpenAPI 문서에 정확히 노출된다.
- [ ] 성공 응답에는 구조 검증된 제안이 정확히 3개 포함된다.
- [ ] 응답의 제안 카드는 각각 비어 있지 않은 제목과 설명 목록을 가진다.
- [ ] 참조 파일이 없을 때 파일 목록은 빈 배열이고 임의 파일명은 반환되지 않는다.
- [ ] 참조 파일이 있을 때 사용자/프로젝트 소유권이 검증되고, 실제 서버 파일명만 반환된다.
- [ ] 포커스 항목은 응답에서 전달되며 프런트엔드는 고정 더미 배지에 의존하지 않는다.
- [ ] LLM의 malformed output, timeout, 공급자 장애가 명시적인 오류 응답으로 변환된다.
- [ ] 프런트엔드의 단계별 로딩은 API 대기 UX로만 처리되며 백엔드 sleep으로 구현되지 않는다.
- [ ] 오류 시 프런트엔드에 실패 toast가 나타나고 입력이 유지된다.
- [ ] 인증, 권한, 입력 경계, 파일 권한, 모델 응답 검증 테스트가 통과한다.
- [ ] 실제 공급자 키/모델 호출 없이도 mock 기반 테스트를 반복 실행할 수 있다.

## 14. 구현 전 결정 사항

| 결정 항목                | 현재 확인된 상태                                                 | 담당자가 결정할 내용                             |
| ------------------------ | ---------------------------------------------------------------- | ------------------------------------------------ |
| API 서버 저장소/기본 URL | 프런트 저장소의 API 클라이언트는 `NEXT_PUBLIC_API_BASE_URL` 사용 | FastAPI 저장소, 개발/스테이징 URL, CORS          |
| 인증                     | 프런트엔드에 기존 API 클라이언트와 인증 관련 모듈이 있음         | FastAPI에서 세션/JWT를 검증하는 방식             |
| 프로젝트 모델            | 프런트 `store/workspace.ts`에는 화면 탭 상태만 확인됨            | 프로젝트 ID의 위치, 필수 여부, 권한 정책         |
| 파일 업로드              | AppContext 첨부 버튼과 실제 업로드 미연결                        | 기존 업로드 API 재사용 또는 신규 업로드 endpoint |
| 파일 형식 및 한도        | 확정되지 않음                                                    | 허용 확장자, MIME, 크기, 개수, 추출기            |
| LLM 제공자/모델          | 확정되지 않음                                                    | 데이터 처리 위치, 비용/지연 한도, 모델 버전      |
| 결과 저장/이력           | 확정되지 않음                                                    | 저장 여부, 보존 기간, 삭제, 조회 API             |
| 동기/비동기              | 첫 구현 동기 JSON 권장                                           | 실제 응답시간 측정 후 job/polling/SSE 필요 여부  |

이 항목들이 미결정이어도 프롬프트/응답 스키마와 mock 기반 API 계약 테스트를 먼저 구현할 수 있습니다. 다만 파일을 실제 분석 근거로 쓰려면 업로드, 파일 소유권, 추출 완료 상태에 대한 결정이 필요합니다.
